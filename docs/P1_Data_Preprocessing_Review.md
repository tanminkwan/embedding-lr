# P1_Data_Preprocessing_Review — Phase 1 데이터 전처리 필요성 검토

## 1. 목적

`data/v0.1_from.Claude-Cowork/` 에 이미 생성되어 있는 Phase 1 합성 데이터를 임베딩(Phase 2, RAG API `POST /api/embeddings`)에 투입하기 전, [[Scope_Definition]]의 "노이즈(스택 트레이스, 코드 블록 등) 제거로 데이터 순도 확보" 요구사항 대비 실제 데이터 상태를 점검한다.

## 2. 검토 대상

| 파일 | 용도 | 파싱 결과(행 수) |
|---|---|---|
| `data.csv` | 전체 통합본 | 1,005 (파싱 오류 6행 포함) |
| `train.csv` | 학습셋 | 600 |
| `test.csv` | 테스트셋 | 205 (파싱 오류 6행 포함) |
| `val.csv` | 검증셋 | 200 |
| `role_01~09_*.csv` | 역할별 원본 | 각 40건(IT) / 200건(NON_IT) |

**데이터 파이프라인 구조**: `role_01~09_*.csv`(역할별 원본) 9개 파일을 그대로 이어붙여(concat) `data.csv`(1,000건)를 만들고, `data.csv`를 클래스별로 **3:1:1 비율로 임의(random) 분할**하여 `train.csv`(클래스당 120건)·`test.csv`(클래스당 40건)·`val.csv`(클래스당 40건)를 생성한다(Scope Definition 3.3절 규모와 동일). 임의 분할이기 때문에, 3.1의 `role_03_network.csv` 손상 레코드가 우연히 test 분할 쪽에 배정된 것 — 재생성 시마다(랜덤 시드가 고정되어 있지 않다면) 결손이 어느 분할에 떨어질지는 달라질 수 있다.

검토 방법: Python `csv.DictReader`로 각 파일을 로드하여 (a) `카테고리` 값이 5개 클래스 열거값과 일치하는지, (b) 결측/중복/공백 이상 여부, (c) 인코딩·개행 문자, (d) 응답 본문 내 마크다운 코드블록(\`\`\`) 및 스택트레이스 패턴 존재 여부를 확인.

## 3. 발견 사항

### 3.1 [필수 수정] `role_03_network.csv` CSV 이스케이프 오류 → 데이터 손실

- **현상**: `role_03_network.csv`의 한 레코드 응답 본문에 `show log traffic | match 10.0.0.5"` 처럼 **이스케이프되지 않은 `"` 문자**가 포함되어 있음(CSV 규칙상 필드 내 `"`는 `""`로 이중 처리해야 함).
- **영향**: 이 홑따옴표 이후 CSV 파서가 필드 경계를 잘못 인식하여, 해당 레코드 이후 5줄이 별도의 깨진 레코드로 분리됨. 결과적으로 **정상 레코드 1건이 파괴되고 파싱 불가능한 쓰레기 행 5건이 생성**됨.
- **파급 범위**: `role_03_network.csv` → `data.csv`(통합 시 그대로 포함) → `test.csv`(네트워크 역할 데이터가 test 분할에 배치됨)로 전파.
  - `data.csv`: IT 199건 (정상 200건 대비 1건 부족) + 파싱 오류 행 6건
  - `test.csv`: IT 39건 (정상 40건 대비 1건 부족) + 파싱 오류 행 6건
  - `train.csv`, `val.csv`, `role_01/02/04/05`는 영향 없음(정상 40건씩)
- **조치 필요**: `role_01~09_*.csv`가 원본(source of truth)이고 `data.csv`는 9개 role 파일을 재조합한 결과물, `train/test/val.csv`는 다시 `data.csv`를 분할한 결과물이다. 따라서 **수정은 반드시 원본인 `role_03_network.csv`에서 시작**해야 하며, `data.csv`나 `test.csv`를 직접 고치면 다음 재조합/재분할 시 수정 내용이 덮어써져 사라진다.
  1. `role_03_network.csv`에서 문제의 `"` 문자를 `""`로 이스케이프(또는 문제 문자 제거)
  2. `role_01~09_*.csv` 9개 파일을 재조합하여 `data.csv` 재생성 (1,000건, 클래스당 200건 균등 분배 복원)
  3. 재생성된 `data.csv`를 다시 `train.csv`(120/클래스)·`test.csv`(40/클래스)·`val.csv`(40/클래스)로 재분할

  **임베딩 API 호출 전 반드시 이 순서로 수정** — 그대로 진행 시 IT 클래스 학습/평가 데이터가 1건씩 누락되고, 6건의 깨진 행이 임베딩 대상에 포함되어 노이즈로 작동함.

### 3.2 [권장] 마크다운 코드펜스(\`\`\`) 정리

- IT 카테고리 응답의 **약 38.7%(199건 중 77건)** 에 \`\`\`bash 등 마크다운 코드펜스가 포함됨(예: `nginx -t`, `jeusadmin ... domain-status` 같은 짧은 명령어).
- 단, Java/서버 로그성 **스택트레이스 패턴(`Exception`, `Caused by`, `at ...(`, `Traceback`)은 전 카테고리에서 0건** — Scope Definition이 우려한 "스택 트레이스 노이즈"는 현재 데이터에는 존재하지 않음.
- 코드펜스 안의 명령어 자체는 IT/비-IT 판별에 유효한 신호(의미 있는 텍스트)이므로 **본문은 보존**하되, 펜스 구분자(\`\`\`, \`\`\`bash)는 임베딩 대상 텍스트를 구성할 때 제거하는 것을 권장.

  **제거 이유 (정정)**: BGE-M3가 \`\`\`bash 같은 문자열을 못 읽거나 임베딩이 손상되는 것은 아님 — 그냥 평범한 토큰으로 인코딩되어 벡터에 반영될 뿐이라 "오염"이라는 표현은 부정확함. 실제 이유는 두 가지:
  1. **신호 희석**: 질의·응답이 짧은 텍스트(응답 평균 56자)라 토큰 하나의 비중이 크다. 코드펜스 구분자는 주제 분류에 의미가 없는데 벡터 표현의 일부를 차지해, 실제 의미 있는 명령어·문맥 신호의 비중을 상대적으로 낮춘다.
  2. **학습 지름길(leakage) 위험 — 더 중요**: NON_IT 4개 카테고리에는 코드펜스가 0건 등장하고 IT에만 38.7% 등장한다. 즉 "백틱이 있으면 IT"라는 매우 강한 표면적 단서가 존재해서, LR이 임베딩이 담고 있는 질의의 실제 의미보다 이 표면 패턴에 의존해 결정 경계를 학습할 위험이 있다. 추론 시 실제 사용자 질의는 마크다운 포맷 없이 들어오는 경우가 많으므로(운영 로그에는 백틱이 없음), 이런 지름길 학습은 실제 데이터에 대한 일반화 성능을 떨어뜨릴 수 있다.

  3.1의 CSV 파싱 사고 원인도 코드펜스·특수문자가 포함된 응답에서 발생한 만큼, 정제 규칙을 명시해두는 것이 데이터 순도 확보와 CSV 안정성 양쪽에 모두 안전함.

### 3.3 [문제 없음] 그 외 항목

| 항목 | 결과 |
|---|---|
| 결측값(`질의`/`응답` 공백) | 0건 |
| 중복 레코드 (`질의`+`카테고리` 기준) | 0건 |
| 필드 앞뒤 공백 오염 | 0건 |
| 인코딩 | UTF-8, BOM 없음 |
| 개행 문자 | CRLF 없음(전부 `\n`). 응답 198/999건(19.8%)이 여러 줄로 구성된 목록형 답변 — 정상적인 형식이며 손상 아님 |
| 텍스트 길이 | 질의 2~63자, 응답 8~671자 — 극단적으로 짧거나(임베딩 무의미) 긴(토큰 초과) 이상치 없음 |

## 4. 결론 및 권장 조치

**전처리가 필요함.** 다만 Scope Definition이 예상한 "스택트레이스 제거" 규모의 작업은 아니고, 실제로는 다음 2가지로 한정됨.

1. **(필수, 선행)** 원본 `role_03_network.csv`의 CSV 이스케이프 오류를 수정 → `role_01~09_*.csv` 재조합으로 `data.csv` 재생성 → `data.csv`를 `train/test/val.csv`로 재분할. **반드시 이 순서(role → data → train/test/val)로 진행** — `data.csv`나 `test.csv`를 개별적으로 손으로 고치면 원본(role 파일)과 어긋나 다음 재생성 시 수정이 사라짐. Phase 2 임베딩 호출 전에 반드시 완료해야 함. 수정 없이 진행하면 IT 클래스 학습 데이터가 클래스당 200건 균등 분배 전제를 깨고, 6건의 깨진 행이 그대로 임베딩·학습에 유입됨.
2. **(권장)** 임베딩 입력 텍스트 생성 시 마크다운 코드펜스 구분자(\`\`\`, \`\`\`bash 등)만 제거하고 본문 명령어는 유지하는 경량 정규화 단계를 Phase 2 전처리 함수에 포함.

그 외(결측·중복·인코딩·개행) 항목은 정상이므로 별도 조치가 불필요함.

## 5. 후속 결정 (v0.2 갱신)

3.1절의 근본 원인(CSV가 필드 내 따옴표·쉼표·개행을 이스케이프 규칙에 의존해서만 다룰 수
있다는 구조적 한계)을 고려해, v0.2부터는 출력 포맷 자체를 **CSV → JSONL**로 전환하기로
결정함([[Scope_Definition]] 3.3절, [[P1_요구사항정의서_DataPreparation]] 참고). 위 1번 조치
(원본 수정 → 재조합 → 재분할 순서)는 포맷과 무관하게 그대로 적용되지만, 산출물 확장자는
`role_01~09_*.jsonl` → `data.jsonl` → `train/test/val.jsonl`로 바뀐다. JSONL 전환 이후에는
RFC4180 이스케이프 규칙 자체가 필요 없어져 이 유형의 파싱 사고가 구조적으로 재발할 수 없다.
