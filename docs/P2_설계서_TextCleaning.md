# 설계서 — Phase 2 텍스트 전처리 (TextCleaning)

[[Architecture_Design]] 2절(모듈 구조: `preprocessing/text_cleaner.py`)에서 이름만 정의된
모듈의 정확한 함수 시그니처·규칙을 확정하는 설계서. "왜 필요한가"는 [[Scope_Definition]]
2절(텍스트 전처리 요구사항)과 [[P1_Data_Preprocessing_Review]] 3.2절(코드펜스 분석)이
이미 답했으므로, [[P0_설계서_Common]]과 동일한 방식으로 별도 요구사항정의서 없이 이
설계서로 바로 진행한다.

대상 모듈: `preprocessing/text_cleaner.py`. Phase 2 임베딩 파이프라인과 Phase 5 추론
경로가 이 모듈을 동일하게 공유한다([[Architecture_Design]] 4절).

## 1. 목적 및 원칙

임베딩 입력에서 **의미 없는 형식적 노이즈만** 제거하고, 분류 판단에 실제로 쓰이는
**본문 신호는 보존**한다. 이 원칙을 어기면 두 방향으로 실패한다.

- 너무 적게 지우면: 형식적 잡음(코드펜스 구분자, 스택 트레이스 boilerplate, 중복
  공백)이 벡터 표현의 일부를 차지해 실제 의미 신호의 비중을 낮춘다([[P1_Data_Preprocessing_Review]]
  3.2절 "신호 희석").
- 너무 많이 지우면(예: 코드 블록 전체 삭제): 본문 명령어처럼 IT/비-IT 판별에 유효한
  신호까지 사라진다. 또한 "이 텍스트에 코드펜스가 있는가" 같은 표면적 패턴에 모델이
  의존하는 지름길 학습(leakage) 위험도 있다 — 지우는 것은 패턴 자체(구분자)여야 하고,
  그 패턴이 있었다는 사실이 결과에 남아서는 안 된다.

## 2. 함수 시그니처

```python
def clean_text(text: str) -> str:
    """형식적 노이즈 제거. 순서 고정: 코드펜스 구분자 제거 → 스택 트레이스 라인 제거
    → 공백 정규화. 이 순서를 바꾸면 안 된다(3절 참고)."""
```

- **입력/출력 계약**: 정제 대상 문자열 **1개**만 받는다. `질의`+`응답` JSONL 레코드 키를
  하나의 임베딩 입력 문자열로 합치는 책임은 이 함수에 두지 않는다 — 결합은
  `embedding/pipeline.py`(학습 경로)와 `inference/predictor.py`(추론 경로) 호출부의
  책임이다([[CLAUDE.md]] 1절 SRP — "정제"와 "결합"은 별도 관심사).
- 순수 함수다. 외부 의존성(AIPro+ 호출, 파일 I/O) 없음 — 같은 입력은 항상 같은 출력.

## 3. 규칙 상세 (적용 순서 고정)

### 3.1 마크다운 코드펜스 구분자 제거

- 대상: ` ``` ` 또는 ` ```<language> `(예: ` ```bash `) 형태의 펜스 구분자 줄.
- 처리: 구분자만 제거하고 **본문(코드/명령어)은 그대로 보존**한다.
- 근거: 코드펜스 안 명령어(`nginx -t` 등)는 IT/비-IT 판별에 유효한 신호이므로 삭제
  대상이 아니다. 반면 구분자 자체는 NON_IT 카테고리에는 0건, IT에만 약 38.7% 등장하는
  표면적 패턴이라 leakage 위험이 있다([[P1_Data_Preprocessing_Review]] 3.2절) — 그래서
  "구분자만" 제거가 정확한 스코프다.

### 3.2 스택 트레이스 / 트레이스백 라인 제거

- 대상: 아래 패턴 중 하나라도 매칭되는 **줄 단위**로 제거한다(부분 문자열이 아니라
  라인 전체 삭제).
  - `Exception`
  - `Caused by`
  - `at \S+\(` (Java 스택 프레임 패턴)
  - `Traceback`
- 근거: [[Scope_Definition]] 2절이 원래 우려한 노이즈이며, v0.1 데이터에는 0건이었지만
  ([[P1_Data_Preprocessing_Review]] 3.2절) `text_cleaner`는 Phase 5 추론 경로에서 실사용자
  입력도 처리하므로, 운영 중 스택 트레이스가 섞여 들어올 가능성에 대비해 방어적으로
  포함한다. 스택 트레이스 라인은 (코드펜스 본문과 달리) boilerplate이지 분류 신호가
  아니므로 라인 전체를 지워도 정보 손실이 아니다.

### 3.3 공백/개행 정규화

- 연속된 공백 문자(스페이스 2개 이상)를 스페이스 1개로 축약.
- 연속된 개행(빈 줄 2개 이상, 3.1/3.2에서 줄을 지운 후 생기는 빈 줄 포함)을 개행 1개로
  축약.
- 문자열 앞뒤 공백은 `strip()`.
- 근거: 공백/개행 자체는 임베딩 의미에 기여하지 않는데, 3.1/3.2에서 줄을 제거하고 나면
  빈 줄이 남으므로 **반드시 마지막 단계**로 실행해 정리한다.

## 4. 순서가 중요한 이유

1. 코드펜스 구분자를 먼저 제거해야, 이후 스택 트레이스 라인 검사가 펜스 마커 때문에
   흐트러지지 않는다.
2. 스택 트레이스 라인 제거는 텍스트 중간에 빈 줄을 남길 수 있으므로, 공백 정규화보다
   먼저 실행되어야 그 빈 줄이 최종적으로 정리된다.
3. 공백 정규화가 마지막이어야 위 두 단계가 만든 부산물(중복 공백/빈 줄)까지 깨끗하게
   정리된다.

## 5. 테스트 등급

[[CLAUDE.md]] 2절 등급표 기준 **A등급**(핵심 순수 로직, `preprocessing/text_cleaner`로
이미 명시됨) — Red→Green→Refactor로 테스트 먼저 작성, 라인 커버리지 ≥ 90%. 최소 케이스:

- 코드펜스 구분자 제거 + 본문 보존 (언어 태그 있는 경우/없는 경우)
- 스택 트레이스 4개 패턴(`Exception`/`Caused by`/`at ...(`/`Traceback`) 각각 라인 제거
- 스택 트레이스가 아닌 일반 문장은 보존(오탐 방지 — 예: "Exception 처리 방법 알려줘"처럼
  스택 트레이스가 아닌 일반 질의 문장에 `Exception`이라는 단어만 포함된 경우의 처리
  방침은 코드 구현 시 확정한다)
- 연속 공백/개행 정규화, 문자열 앞뒤 공백 제거
- 위 3규칙이 함께 적용된 복합 입력에 대한 통합 케이스(순서 검증)
- 빈 문자열, 노이즈가 전혀 없는 입력(no-op) 케이스
